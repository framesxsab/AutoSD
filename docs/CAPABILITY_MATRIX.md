# AutoSD Release Capability Matrix

**Scope: the v1.0 release line.** This document is the single source of truth for what AutoSD claims about its own capabilities. Every README sentence, release note, and marketing phrase must match a row here. If a claim is not on this matrix, it does not go in the README.

Last reviewed: 275 tests across 49 files, all green (`npm test`). The v1.0.0 tree was 219/43; the suite grew via evaluation, hardening and plug-in tests (see `evaluation.baseline.json`). The deterministic demo export is `demoVersion: 2` — it adds a reader-pagination step and a `reader` field; byte-stability guarantees are unchanged. No benchmarks are published anywhere in this document because no evaluation harness exists yet.

## Status definitions

These four labels are used consistently and never blurred:

- **IMPLEMENTED**: shipped code with passing coverage. The structural claim only; it says nothing about validation depth.
- **SOFTWARE-VALIDATED**: implemented and verified in software (automated tests, the deterministic demo, automated audits). No hardware involved.
- **HARDWARE-DEPENDENT**: code ships, but real behavior depends on physical hardware we do not control and have not validated against. Contract tests cover fallback behavior only.
- **USER-VALIDATION-PENDING**: works in software, but whether it works _for people_ is unproven until blind and low-vision users test it. No user study has been run.

> **Hard boundary:** `SOFTWARE-VALIDATED` never implies `HARDWARE-DEPENDENT`/`USER-VALIDATION-PENDING` is satisfied. A green test suite and a passing `npm run evaluate` prove the software contract only — the capability matrix row stays at its current status until the evidence listed in “What would move the status” is produced.

## Rules for moving a row

1. A row moves to SOFTWARE-VALIDATED only with named automated evidence: a test file, the deterministic demo, or an automated audit. "It should work" moves nothing.
2. HARDWARE-DEPENDENT rows move only after a documented session with real hardware, including what failed.
3. USER-VALIDATION-PENDING rows move only after a study with actual blind and low-vision participants, with methodology published.
4. Nothing regresses silently. If code changes break the evidence behind a row, the row moves back and the README changes with it.

## Explicitly not started

Listed so nobody has to guess:

- Recall@k evaluation harness. Roadmap item, no published numbers exist.
- Networked marketplace installs. The catalog is an in-repo fixture today.
- Plugin sandboxing. Roadmap item.
- Any form of tactile user study or screen-reader user testing.

## Language rules for release docs

- Say "software-validated", never just "validated", when tests are the evidence.
- Say "hardware-dependent" when physical devices are involved. Never write that any specific display works.
- Never imply tactile output has been read by a human. The correct phrasing is "byte-stable and device-portable, not proven-readable".
- Personas in [PRD.md](../PRD.md) are design targets, not users. There is no user base to cite.
